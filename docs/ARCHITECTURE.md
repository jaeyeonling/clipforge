# clipforge 아키텍처 설계 (v1 초안, 2026-10-18)

> 제품(방송용 통합 프로그램)으로 확장하는 설계는 [PRODUCT_ARCHITECTURE.md](PRODUCT_ARCHITECTURE.md). 이 문서는 분석 코어(신호·판정·평가)의 설계와 실험 기록이다.

> 참고 레포 6개(AutoEditor, Auto-clipper, auto-highlighter, automated-content-pipeline, vod-to-viral, crispy)와
> 로컬 환경 실측(RTX 4070 SUPER, FFmpeg 9.0.2)을 바탕으로 정리. 각 결정의 근거는 절 끝의 `근거:` 참조.

## 0. 조사에서 확인한 사실

| 항목 | 확인 내용 | 설계 반영 |
|---|---|---|
| 업계 표준 파이프라인 | 전부 동일: ffmpeg 추출 → **1초 단위 시계열** → 정규화 → 임계/피크 → 최소간격 디듀프(15~20s) → 고정 패딩 컷 → 폴더+JSON | 현재 clipforge 뼈대가 이미 이 구조. 유지 |
| 융합 방식 | 모두 하드코딩 선형 가중합(70/30, 35/30/25/10). 학습 융합 없음 | 가중합 유지 + Auto-clipper의 **동의 보너스**, **억제 마스크** 추가 |
| 평가 | 6개 중 e-kemeny 1개만 GT 대비 P/R/F1(영상 1개). 나머지 전무 | **평가 루프가 이 프로젝트의 차별점**. 정답 생성 비용을 줄이는 `align`이 핵심 |
| 게임 UI 신호 | AutoEditor: YOLO 38클래스로 UI 상태 이벤트 → 프레임 집합 연산. crispy: 게임별 고정 crop + 소형 분류기. Auto-clipper: 게임별 HSV 범위를 데이터(dict)로 | 게임 프로필을 **데이터 파일**로 분리. YOLO는 최후 수단, 색 마스크/템플릿/OCR 먼저 |
| D2R 아이템 인식 | d2r-image(2022 중단, tesserocr 의존). 방식은 재사용 가능: HSV 색 마스크(gold/green/orange…) → 어두운 라벨 박스 contour → OCR psm7 → 이름 사전 매칭 | 라이브러리 의존 대신 **방식만 자체 구현**. 색 범위 상수는 차용 |
| Whisper 트리거 | Auto-clipper: 트리거 단어 시각 t → `[t-30, t+5]` 창, 10s cooldown | 이벤트→곡선 어댑터의 기본 커널로 채택 |
| Premiere 출력 | AutoEditor: xmeml v5를 ElementTree로 직접 생성. 컷을 이어붙임 | xmeml 직접 생성. 단 **원본 타임라인 위치 유지 + 마커** (사람 마감용) |
| 하드웨어 | NVDEC 동작 확인. 1080p60 60s: 디코드만 3.7s, 프록시(libx264)+썸네일 5.6~6.3s. **병목은 인코딩**, 디코딩 아님 | 프록시는 기본 생략(lazy). 프레임 추출만 기본 |
| FFmpeg 빌드 | `--enable-whisper`(whisper.cpp 필터), `--enable-chromaprint` 내장 | Python CUDA 의존성 없이 전사·음성 지문 가능. 옵션으로 보유 |

## 1. 목표와 단계 (2026-10-18 결정)

**Phase 1 — 편집본 → 쇼츠.** 친구의 완성 편집본(10~15분, 4K60)에서 쇼츠로 뽑을 30~60초 구간을 골라 Premiere 세로(1080×1920) 시퀀스 + 검토용 mp4 초안으로 낸다.
- 입력이 이미 하이라이트 밀도가 높으므로 문제는 "걸러내기"가 아니라 **"순위 매기기"**. 지표는 recall보다 **hit@K**(상위 K개 후보 중 친구가 실제로 고른 것)가 1순위.
- 정답: 친구가 이미 올린 쇼츠가 있으면 `align`으로 편집본에 역매핑. 없으면 `export → keep/ → harvest` 루프로 친구/우리가 고른 것이 정답.
- 편집본에만 있는 신호를 적극 활용: 득템 배너 갱신, 삽입 설명 카드(친구가 강조한 지점), 컷 밀도(잘게 자른 구간 = 긴장), 채팅 오버레이 변화율, 후원 알림, 발화 키워드.

**Phase 2 — 원본 녹화 → 편집본.** Phase 1에서 신호·평가 루프가 의미 있는 숫자를 내면, 같은 하네스에 2시간 원본을 넣고 친구 편집본을 `align`해 정답을 만들어 recall/coverage로 진행. (0~5절 대부분이 이 단계를 위한 설계이며 그대로 유효)

두 단계는 **같은 코드**를 쓴다. 다른 것은 입력 영상, 정답의 출처, 1순위 지표, 출력 시퀀스 포맷뿐. 게임 프로필·신호 플러그인·판정 층·평가는 공유.

**비목표(당분간)**: 업로드, 자막 생성, BGM, 완전 자동 편집. 세로 리프레이밍은 Premiere 모션 파라미터(스케일/위치)로만 — 얼굴 추적 같은 건 안 함.

## 2. 레이어 구조

```
videos/<id>.mp4 ─▶ L0 prep ─▶ cache/<id>/{meta.json, audio.wav, frames/}
                                 │
                   L1 signals ◀──┤  games/<game>.yaml (ROI, 색범위, 템플릿, 키워드)
                   Curve | Events│
                                 ▼
                   L2 decide ── events→curve 어댑터 → 가중합 + 동의보너스 × 억제마스크 → 임계 → 군집 → candidates.json (+evidence)
                                 │
         ┌── L3 eval ◀───────────┼──────────▶ L4 output ── review/<id>/*.mp4 ─ keep/ ─ harvest
         │   recall/coverage     │                       └─ premiere/<id>.xml (마커 + 세그먼트 트랙)
         │   라벨별 · 놓친 구간   │
         └── labels/<id>.csv ◀── align (친구 최종본 ↔ 원본 자동 정렬) ◀── finals/<id>.mp4
```

### L0 prep — 한 번만 디코딩
- `meta.json`: ffprobe + `game` 필드(파일명 규칙 또는 `--game`).
- `audio.wav`: 16kHz mono. (Whisper·음량·음성지문 공용 입력)
- `frames/%06d.jpg`: **1fps, 세로 720px**. OCR이 읽을 수 있는 최소 해상도(D2R 라벨 글자 9~27px@720p). 2시간 ≈ 7,200장 ≈ 500MB.
  - 기존 360p `thumbs/`는 폐기. `frame_motion`은 메모리에서 160×90으로 축소해 사용.
- `proxy.mp4`: **기본 생략**. `--proxy` 시 NVENC(h264_nvenc, cq 30)로 별도 패스. VLM/장면 검토용으로 필요할 때만.
- 디코딩: `-hwaccel cuda` 시도 → 실패 시 CPU. (현재 코드 유지)
- 예상 시간(2h 1080p60): 디코드+JPEG ≈ 8~12분, 오디오 ≈ 20초.

근거: 실측에서 디코드 3.7s/60s vs 프록시 포함 6s. 프록시가 시간의 40%를 먹는데 1차 신호들은 쓰지 않음.

### L1 signals — 교체 가능한 플러그인
인터페이스 유지: `@signal(name) def f(cache, profile) -> Curve | Events`. `profile`(게임 프로필) 인자만 추가.

| 신호 | 타입 | 출력 | 비고 |
|---|---|---|---|
| `audio_loudness` | Curve | dB rel. median, hop 0.5 | 현재 구현. 베이스라인 |
| `audio_spike` | Curve | 직전 5s 평균 대비 상승분 | e-kemeny 방식. 지속적 큰 소리(전투 BGM)와 "갑자기 큰 소리"를 구분 |
| `frame_motion` | Curve | 1fps 프레임차 | 현재 구현 |
| `ui_state` | Events(mask) | `{town, inventory, menu, loading, dungeon_select}` 구간 | 게임 프로필의 템플릿/색 ROI로 판정. **억제 마스크**로 사용 |
| `item_banner` | Events | `{t, added_text}` | **D2 1순위.** 좌상단 "득템 :" 배너 ROI를 3초 coarse OCR → 변화 구간만 1초, 안정 상태 전이에서 글자가 늘어난 시각을 이벤트로. 6.1절 참조 |
| `edit_emphasis` | Events | `{t_start, t_end, kind}` | **Phase 1 전용.** 편집본에서 배너 소실·흰 카드·타이틀 자막 구간 = 친구가 줌/카드로 강조한 지점. 쇼츠 후보 순위에 직접 반영 |
| `cut_density` | Curve | 30초 창 내 scdet 컷 수 | **Phase 1 전용.** 잘게 자른 구간 = 긴장. ffmpeg `scdet=t=10` 로그 파싱 |
| `d2_item_label` | Events | `{t, quality, text, matched_name}` | HSV 마스크(gold/green/orange/yellow) → 어두운 박스 contour → OCR → 이름 사전(rapidfuzz). 룬·유니크·세트만 이벤트. 배너에 안 적히는 드랍 보완용 |
| `dnf_result` | Events | 던전 클리어/결과창, 보스 HP 0 | 템플릿 매칭(TM_CCOEFF_NORMED ≥ 0.8) |
| `speech_keyword` | Events | 전사에서 리액션/득템 어휘 시각 (강·중·약·득템 그룹, cooldown 8s) | ✅ `transcribe.py`: faster-whisper(GPU) → ffmpeg whisper 필터 폴백. 사전은 `games/common.yaml` |
| `speech_energy` | Curve | 발화 구간의 음성 에너지(비BGM) | VAD 기반. 리액션 보강 |

캐시 키: `cache/<id>/<signal>.json`에 `meta.params_hash` 기록. 프로필/파라미터가 바뀌면 자동 재계산, 아니면 스킵.

### L2 decide — 판정 층
현재 `make_candidates`를 다음 순서로 확장:

1. **Events → Curve 어댑터**: 이벤트 하나를 비대칭 커널로 펼침. 기본 `[t-pre, t+post]` 사다리꼴(예: 룬 드랍 `pre=8, post=4`; 음성 키워드 `pre=30, post=5` — Auto-clipper 값). 커널 파라미터는 신호별로 프로필에.
2. **정규화**: Curve는 z-score(현재), Events 어댑터 출력은 0~1.
3. **가중합 + 동의 보너스**: `score = Σ w_i·s_i`, 0.2 이상인 신호가 2개면 ×1.15, 3개면 ×1.3.
4. **억제 마스크**: `ui_state`의 town/inventory/menu/loading 구간은 score×0 (또는 ×0.2). 메뉴에서 소리만 커지는 오탐 제거.
5. **임계 → 군집**: 임계 초과 → `merge_gap`(3~5s) 병합 → `clamp(span + pad, min_len, max_len)`.
6. **최소 보장**: 후보가 `duration/600`개 미만이면 임계를 ×0.5로 내려 보충(Auto-clipper fallback).
7. **evidence**: 각 후보에 `{signal: peak_value}`와 발화 이벤트 목록 기록. eval에서 "어느 신호가 잡았나"를 라벨별로 집계하는 데 쓴다.

판정 층은 나중에 같은 입력(신호 테이블)·같은 출력(Segments)을 내는 작은 분류기(로지스틱/GBDT)로 교체. 레이블 수백 개 쌓인 뒤.

### L3 eval — 결정의 근거
- 현재 `evaluate.py` 유지(recall / precision / coverage / 라벨별 / 놓친 구간).
- 추가: **신호별 기여도** — 각 정답 구간에서 어떤 신호가 임계를 넘었는지 → "rune_drop은 d2_item_label만 잡고 음량은 못 잡음" 같은 표.
- 추가: `sweep`에 가중치 그리드도 포함, 결과를 `reports/<id>_<ts>.md`로 저장해 실험 이력 남김.
- 허용 오차: 겹침 ≥ 1s(현재). 친구 컷은 보통 3~15s라 적절.

### `align` — 정답 데이터 자동 생성 (신규, 최우선)
> 조사한 모든 레포가 평가를 못 한 이유는 정답 만들기가 비싸서다. 친구의 **최종본**이 있으면 정답은 이미 존재한다.

- 입력: `finals/<id>.mp4`(유튜브 업로드본) + `cache/<id>/audio.wav`.
- 방법 A(1차): **오디오 랜드마크 지문**(Shazam식 스펙트로그램 피크 해시, 2~3초 창). 최종본의 각 창이 원본의 어느 시각에 매칭되는지 → 연속 매칭을 구간으로 병합 → `labels/<id>.csv`에 `label=kept, note=auto`.
  - BGM 추가·볼륨 변경·컷 전환에 강함. 발화/게임 효과음이 살아 있으면 매칭됨.
- 방법 B(보조): 프레임 pHash(2fps) 시퀀스 정렬. 오디오를 전부 바꾼 구간 대비.
- 검증: 합성 테스트 — 원본에서 임의 구간 10개를 잘라 BGM 섞어 붙인 가짜 최종본으로 recall 측정.
- 이후 사람이 하는 일은 자동 구간에 **라벨 범주만 붙이기**(rune_drop/reaction/fail/…). 30분 영상 라벨링이 2시간 → 10분.

### L4 output
- `export`: 후보를 mp4로 — NVENC로 교체(libx264 veryfast 대비 수 배 빠름). 파일명에 evidence 요약 포함(`012_0-19-30_2.1_loud+rune.mp4`).
- `harvest`: 현재 유지.
- `xml`(신규): xmeml v5 직접 생성. **마커와 세그먼트 트랙을 한 시퀀스에 둘 다** 넣는다(결정됨).
  - 리뷰 시퀀스(원본 해상도·fps): **V1 = 원본 전체 1클립**, **V2 = 후보 세그먼트만 원본 시각 위치에**(갭 유지), 시퀀스 마커 = 후보(이름 `score|evidence`, 색은 라벨별). 친구는 마커로 훑고 V2에서 리플 삭제하면 컷 편집본.
  - 쇼츠 시퀀스(Phase 1): 후보마다 **1080×1920 시퀀스 1개**. 클립에 `Basic Motion` 스케일/위치를 넣어 게임 화면 중앙(캐릭터 주변)이 보이게 크롭. 상단 여백은 제목용 빈 트랙. 득템 배너·채팅 오버레이는 크롭 밖으로 밀려나므로 필요하면 별도 PNG 트랙(후속).
  - 검토용 초안 mp4: 같은 크롭 파라미터로 NVENC 렌더(`export --shorts`). Premiere 열기 전에 빠르게 고르는 용도.
  - `pathurl`은 `file://localhost/C:/...` 형식, `<file>` id 재사용(AutoEditor 결함 회피).
  - OTIO는 나중 선택지(0.17+에서 어댑터가 별도 패키지로 분리됨). 1차는 직접 생성이 단순.

## 3. 게임 프로필 (데이터)

```yaml
# games/d2r.yaml
resolution_ref: [1920, 1080]      # ROI는 이 기준 비율로 저장, 실제 해상도에 스케일
item_colors:                       # HSV (OpenCV 0-180), d2r-image 차용
  gold:   [20, 75, 140, 26, 95, 230]
  green:  [56, 190, 190, 63, 255, 255]
  orange: [20, 190, 190, 23, 255, 255]
  yellow: [27, 110, 190, 33, 145, 255]
label_box: {min_h: 9, max_h: 27, min_w: 40, dark_mean: [4, 25]}
item_names: data/d2r_items.txt     # 룬 33 + 유니크 + 세트
ui_state:
  inventory: {roi: [0.02, 0.08, 0.30, 0.55], template: ui/inventory_frame.png, thr: 0.85}
  town:      {method: minimap_color}
events:
  d2_item_label: {pre: 8, post: 4, weight: 1.5, qualities: [orange, gold, green]}
```

```yaml
# games/common.yaml
speech_keywords: ["미쳤다", "대박", "와", "ㅋㅋ", "아니", "뭐야", "헐", "실화냐"]
speech_kernel: {pre: 30, post: 5, cooldown: 10}
```

DNF도 같은 틀(`games/dnf.yaml`): 결과창 템플릿, 보스 HP바 ROI, 던전 선택창 억제. 한국어 UI OCR은 RapidOCR(ONNX) 한국어 모델로 시작, 품질 부족하면 PaddleOCR.

근거: Auto-clipper의 "게임=설정 dict" 구조는 맞았지만 200KB 단일 파일·추상화 없음은 실패. 파일 분리 + 스키마 검증.

## 4. 저장소 레이아웃 (변경 후)

```
clipforge/
  clipforge/
    run.py            CLI (prep/signals/cands/eval/sweep/export/harvest/align/xml)
    preprocess.py     L0
```

### 6.1 `item_banner` 프로토타입 결과 (`experiments/banner_proto.py`, 같은 영상)
- RapidOCR 한국어 PP-OCRv5 mobile, CPU onnxruntime. 배너 크롭(1700×320) 1장 ≈ 1.4~2.0초. 3초 간격 + 변화 구간 정밀화로 631회 호출, 총 500초. → 1fps 전수 OCR은 비싸므로 **"3초 coarse → 변화 구간만 1초"** 전략을 신호 구현에 그대로 채택. GPU onnxruntime로 가면 수 배 단축 가능.
- 인식 품질: 아이템명 거의 정확(스웹벨트, 레이븐링, 말룬, 기드참(매찬34), 에테강철그늘, 탈라샤 갑옷, 신타이탄, 에테갑옷(방783)). 오인식 패턴: 득템→득렘/특램, 횃불→팻불, ★→츠. **프레임 간 jitter**가 있어 1초 단위 diff는 가짜 이벤트가 많음 → **3초 이상 유지된 "안정 상태" 간 전이**만 이벤트로 (구현에 반영).
- 검출된 득템 추가 이벤트: 4:54 스웹벨트, 6:45 레이븐링, 7:47 기드참(34), 8:33 기드참(23)+에테강철그늘, 10:59 탈라샤갑옷·신타이탄·에테갑옷·드루횃불(편집본이라 여러 개가 한 컷에 몰림). 영상 제목의 "지존참"(3맥20어레20피 스몰참)은 2:51~3:27 사이 추가.
- 모든 이벤트가 scdet 컷 군집(4:50~4:58, 6:52~6:59, 7:40~7:55, 8:27~8:45, 10:58)과 겹침 → 친구는 드랍 순간을 반드시 남긴다. Phase 2에서 이 신호 하나로 drop 계열 recall이 높을 것으로 기대.
- **배너 소실(RESET)도 신호**: 3:30~3:42 배너가 사라진 이유는 친구가 **채팅 오버레이를 줌인**한 편집("헐 지참 나왔어요??"). 즉 배너 RESET ≈ 줌/카드 삽입 ≈ **친구가 강조한 지점**. Phase 1(쇼츠)에서는 이게 가장 직접적인 "친구 취향" 신호. 신호명 `edit_emphasis`(줌·카드·타이틀 구간)로 추가.

## 8. 쇼츠 순위 루브릭 (Phase 1) — 성공 공식 조사를 계산 가능한 점수로 번역

> 출처: 디아2/PoE 득템 쇼츠 실측(한국·해외 30여 편, 조회수·길이), 게임 쇼츠 일반 공식(Buffer 110만 틱톡, Inflow 5,400 쇼츠, Opus/Klap/Vizard/Eklipse 루브릭), 한국 클립 채널 관례(streamhub, Captus, 참타호 모델, 편집 외주 공고), 친구 채널(기준 채널) 관측. 상세는 `docs/research/shorts_formula.md`. 아래 가중치는 **초기값**이며 hit@K로 조정한다.

**실측에서 나온 보정 3가지**
1. 100만 뷰 득템 쇼츠는 두 부류다. **순수 페이오프 9~25초**(아이템이 0~3초에 이미 보이고 리액션이 본체) 와 **서사형 27~60초**(드랍 → 툴팁 감별 → 숫자(원/자룬) → 반전). 후보마다 두 길이 버전을 같이 낸다(`variant: short|story`).
2. 한국 상위 쇼츠는 전부 **첫 프레임 상단 2줄 텍스트 훅 + 원화/룬 단위 숫자**다. 크롭 중심은 캐릭터가 아니라 **인벤토리/툴팁**. → 쇼츠 시퀀스의 크롭은 툴팁이 뜬 순간엔 툴팁 영역으로 이동해야 한다. `item_tooltip` 신호(어두운 툴팁 박스 + 아이템명 OCR, ep59 3:43·11:30에서 관측) 를 Payoff 축에 추가.
3. 대형 스트리머의 날것 클립(MrLlamaSC 71만 구독, 쇼츠 1~7만)은 구독자 대비 저조하고, 편집·서사형(Coooley, 무한게임)이 이긴다. → 우리 출력은 "구간"만이 아니라 **편집 지시**(훅 텍스트 제안, 툴팁 줌 시각, 가치 숫자, 끝 컷 시각)까지 내야 친구가 바로 쓸 수 있다.

### 8.1 조사에서 수렴한 공식

|---|---|---|

### 8.2 후보 생성: 앵커 → 창
쇼츠 후보는 임계 초과 구간이 아니라 **페이오프 앵커**에서 만든다.
- 앵커 소스(우선순위): `item_banner` APPEND → `edit_emphasis`(채팅 줌·카드) → `chat_burst` 피크 → `speech_keyword`(헐/미쳤다/대박) → 음량 스파이크(원본에서만).
- 창: `[anchor − pre, anchor + post]`, pre 기본 12초, post 기본 15초. 경계는 **발화 쉼(무음 ≥0.6초)과 scdet 컷**에 스냅. 편집본에서는 컷을 넘되 컷 2개 이상 걸치면 감점.
- 길이 클램프 15~60초, 목표 25~45초.

### 8.3 점수 (0~1 정규화 후 가중합, 초기 가중치)
| 축 | 특징(계산 방법) | w |
|---|---|---|
| **Payoff** | 창 안에 `item_banner` APPEND 있음(1.0) / 바닥 라벨 유니크·룬(0.7) / 결과창 템플릿(0.7) / 없음(0). 아이템 등급·가치표가 있으면 가중 | 0.35 |
| **Reaction** | 앵커 후 10초 내 리액션 세기: 원본은 음성 에너지 z-score 피크, 편집본은 `edit_emphasis`(줌/카드) 존재 + `speech_keyword` 수 + 후원 알림 | 0.25 |
| **Chat burst** | 채팅 오버레이 ROI의 변화율(1fps 픽셀 diff 또는 OCR 줄 수)이 창 안에서 영상 중앙값 대비 몇 배인가 | 0.15 |
| **Completeness** | 앵커 전 ≥3초의 비메뉴 게임플레이 + 앵커 후 ≥3초 리액션이 창 안에 있음. 창 시작·끝이 발화 중간이면 감점 | 0.15 |
| **Hook quality** | 창 첫 2초: 음성 에너지 또는 이벤트 존재(+), 무음·인벤토리·마을·로딩(−) | 0.10 |
| 감점 | 컷 2개 이상 걸침(−0.1/컷), 길이 15초 미만·60초 초과(−0.2), `ui_state` 메뉴 비율 >30%(−0.2) | |

출력은 후보마다 `{start, end, anchor, score, evidence, hook_mode: "cold_open"|"payoff_flash", overlay_text}`. `overlay_text`는 배너 OCR에서 추가된 아이템명(예: "3맥20어레20피 스몰참")으로 자동 제안.

### 8.3.1 구현 메모 (2026-10-18, ep59 첫 실행)
- 배너 이벤트 라벨을 `append / appear / switch / reset` 로 나눠야 했다. 줌·로딩 뒤 배너가 다시 나타나는 `appear` 와 이벤트 공지 → 득템 배너 교체 `switch` 는 드랍이 아니다. 직전 상태가 비었을 때는 **마지막 진짜 배너**와 비교해야 "사라졌다 다시 나타나며 늘어난" 추가(3:42 스몰참)를 잡는다.
- 채팅 변화율(`chat_burst`) 상위 12초가 전부 2:51~3:41 에 몰렸다 → 편집본에서도 채팅 신호가 살아 있음. Captus 식 "채팅 밀도 = 하이라이트" 가설이 1편에서 확인.
- 앵커 병합 간격 10초, 창 경계 스냅 ±4초(무음 ≥0.4초 또는 scdet 컷). short variant pre 5/post 12, story pre 12/post 22.
- `overlay_text` 는 아직 OCR 원문("템엄슬가3맥20어레20피")이라 8단계 사전 매칭 뒤에야 쓸 수 있다.

### 8.3.2 세로 크롭이 툴팁을 따라가게 (2026-10-18, 친구 피드백 "템 창 띄울 때 중앙 고정이 어색")
- `ui_state` 신호: **패널 제목 OCR**("소지품"/"보관함"/"큐브" → inventory, "캐릭터"/"스킬"/"용병" → left_panel). 제목은 헤더 가운데 고정이라 좁은 ROI(`_panels.py DEFAULT_BANDS`) + 인식 전용 RapidOCR 로 크롭당 0.01~0.05초, 편당 25초. 캐시 `panel_titles.json`.
- 처음 시도한 **HUD 구슬 가림 판정은 틀렸다**: 이 4K 레이아웃에선 패널이 구슬을 안 가리고, 구슬은 중독이면 초록·마나 0이면 검정이 된다. `offscreen`(줌·카드·엔딩) 판정에만 구슬을 쓴다.
- 렌더: `crop_track` 이 ui_state 를 따라 크롭 중심을 0.5 → 0.72(inventory) / 0.28(left_panel) 로 옮기고, ffmpeg `sendcmd` 로 `crop@game x` 를 갱신. **전환은 즉시 점프(컷)** — 패닝은 어색하다는 피드백으로 `--ease 0` 이 기본, `--ease 0.5` 면 패닝. ep59 story 1 에서 소지품 창+툴팁이 통째로 들어온다.
- 남은 것: 바닥 툴팁(인벤 없이 호버)·줌 구간 레터박스·툴팁 위치 자체를 찾는 세밀 추적.

### 8.3.3 창 경계는 말의 경계에 (2026-10-18, 친구 피드백 "말하다가 뜬금없이 끝남")
- 기존 "중앙값 −15dB 무음" 규칙은 마스터링된 편집본에서 쉼을 32개밖에 못 찾아 끝점이 말 중간에 떨어졌다(6개 중 5개).
- 새 규칙 `speech_segments`: 바닥 소음(p10) +12dB 에서 켜지고 +8dB 에서 꺼지는 히스테리시스 에너지 VAD, 20ms 프레임, 0.25s 미만 끊김 병합 → 문장 사이 쉼 189개.
- `snap_end`: 끝점이 발화 중이면 그 발화 끝 +0.3s(최대 8s 연장), 쉼이면 직전 발화 끝 +0.3s. `snap_start`: 발화 시작 −0.3s(최대 4s 당김), 1초 안에 장면 컷이 있으면 컷. 길이 클램프(15~60s)도 발화 끝에서 자른다.
- 부작용: 창이 길어지며 컷 감점이 늘어 순위가 소폭 변동(지존참 story 1→2위). 컷 감점 가중은 친구 keep 이 쌓이면 재조정.
- 전사가 있으면(`transcript.json`) 에너지 VAD 대신 **Whisper 단어 경계**로 발화 구간을 잡는다. 효과음을 말로 오인하지 않고 끝점이 단어 끝에 정확히 붙는다. ep59 적용 후 지존참 story 가 다시 1위(2:38~3:13, 리액션 "와, 뭐야!" 3:13.6 포함).

### 8.3.4 상단 자막 = 전사 대사 + 사전 아이템명 (2026-10-18)
- `suggest_hook`: 1줄째 = 창 안(앵커−3s~끝)에서 `speech_keyword` 가중치(강 3 > 득템 2.5 > 중 1.5)가 가장 큰 대사를 20자로 다듬은 인용("와, 뭐야!", "토 나온다"). 2줄째 = 배너 토큰을 `lexicon` 으로 정규화한 아이템명 + "직득!"(뜻 모르는 약어는 제외). 아이템이 없으면 "채팅 폭발"/"채팅 반응".
- 끝점 직후 3초 안에 리액션 대사가 시작하면 그 대사 끝까지 창을 늘린다 — ep59 의 드랍은 33초 침묵 뒤 193.6s "와, 뭐야!" 로 터지는 구조라 이 규칙이 없으면 리액션이 잘린다.
- `chat_text` 신호(채팅 OCR): rois/chat 을 chat_burst ≥ 0.03 인 초 + 5초마다 OCR(검출+인식, ep59 389회 2분14초), "닉 : 메시지" 줄 재구성, 직전 초와 퍼지 비교해 **새 메시지만** 이벤트(117개). 줌/채팅 앵커 클립의 1줄째는 `chat_keywords`(헐/혈/미쳤/실화/마이갓…) 가중치가 가장 큰 채팅 원문을 “ ” 로 인용. 닉네임은 자막에 안 씀.
- 남은 것: 가치 숫자("현금 7만원")는 `value.yaml` 뒤에. 채팅 OCR 은 띄어쓰기를 자주 잃는다("현금72000원인데") — 자막 전 교정 규칙 필요.

### 8.3.5 대사 자막 (2026-10-18)
- `subtitles.py`: 전사 세그먼트를 클립 구간으로 잘라 큐로. 18자를 넘으면 **단어 타임스탬프**로 나눠 연속 큐(단어가 없으면 길이 비례 시간 분할). 최소 0.6s, 겹침 없음, 마침표 제거.
- 렌더: 클립마다 `.ass`(맑은 고딕 Bold 58px, 흰 글자 + 검은 테두리 4px, 게임 영역 하단 HUD 위 = 하단 여백 620px) 를 ffmpeg `subtitles` 필터(libass)로 굽고, 같은 큐를 `.srt` 로도 떨어뜨린다(Premiere 캡션 임포트용). `--no-subs` 로 생략.
- ep59: 클립당 큐 0~22개. 침묵 구간(2:46~3:03)은 0개 — 정상.

### 8.3.7 첫 친구 피드백 (2026-10-18)
- 초안 6개 중 **1개 컨펌**: 지존참 story(2:38~3:17, 앵커 2:51, 드랍 → 33초 침묵 → "와, 뭐야!"). `labels/ep59.shorts.csv` 에 `keep` 으로 회수. 같은 순간의 채팅 줌 리액션 클립(3:17~3:48)과 짧은 드랍 클립(2:46~3:03)은 고르지 않았다.

### 8.3.8 텍스트 렌더 원칙 (2026-10-18 '참' 사건 뒤)

### 8.3.9 레이아웃 `feed` (2026-10-18, 친구 피드백: @마골 쇼츠 구조가 깔끔)

### 8.4 정답 없이 시작하는 법 — 제목이 곧 약한 정답
친구 채널 영상 제목은 그 회차의 핵심 득템을 명시한다("59일차만에 … 지존참 직득", "56~57일차 … 자룬 직득"). 제목의 아이템명을 배너 OCR의 APPEND 토큰과 퍼지 매칭하면 **그 회차 쇼츠 1순위의 시각이 자동으로 나온다**. 편집본 40여 편 × 1개 = 약 40개의 hit@1 라벨을 공짜로 얻는다. 이것이 Phase 1의 첫 평가 셋. 친구가 후보 중 고른 것(`harvest`)이 쌓이면 그걸로 가중치를 조정한다.

구현(7단계): `episodes.csv`(id, title, url, views …) → `weaklabel` 이 `data/d2r/slang.yaml` 표제어·별칭으로 제목 키워드를 뽑고 rapidfuzz partial_ratio ≥ 85 로 배너 append 토큰과 매칭 → `labels/<id>.shorts.csv` 에 `title_item` 구간(배너 시각 −30s ~ +30s). 정답 창 폭은 **지표를 좋게 보이려고 조정하지 않는다** — ep59 에서 short 1위(3:25 리액션)가 창 밖 4초라 rank 2 로 기록된 채 둔다. 친구 keep 이 쌓이면 그쪽이 진짜 정답.

### 8.5 친구 채널(기준 채널) 관측
- 장편 위주 채널로 **쇼츠는 아직 없음**. 디아2 래더 "노거래 맨땅" 시리즈가 축.
- "몰아보기" 편집본과 가이드 영상이 회차 영상보다 조회가 높다. 득템 회차는 제목에 "(N시간 편집본) X일차만에 … 직득 성공했습니다 !!".
- 7시간 원본 → 11분 40초(보존율 ≈3%). Phase 2의 coverage 목표는 20%가 아니라 **≤10%**가 현실적.
- 시그니처: 득템 배너 누적, 채팅 줌인, 현금 가치 카드. 쇼츠 오버레이 텍스트도 이 톤("현금 7만원 지존참")을 따르는 게 자연스럽다.

## 9. 도메인 지식 보강 계획 (D2R)

> 왜 필요한가: 배너 OCR이 "슬가", "스웹벨트", "3맥20어레20피"를 읽어도 그게 무엇이고 얼마나 귀한지 모르면 Payoff 점수를 못 매기고 오버레이 텍스트("현금 7만원")도 못 만든다. 조사한 모든 성공 사례의 훅이 **아이템 가치 숫자**였다. 도메인 지식은 선택이 아니라 Payoff 축 그 자체다.

### 9.1 네 가지 지식 파일 (전부 `data/d2r/`, git 추적, 시즌별 스냅샷)
| 파일 | 내용 | 1차 소스 | 갱신 |
|---|---|---|---|
| `items.json` | 유니크·세트·룬(33)·룬워드·참 종류·베이스. 필드: `id, name_en, name_ko, kind, tier, aliases[]` | D2R 로컬라이즈 문자열(koKR) 미러, 인벤 D2R DB, maxroll/diablo2.io (영문 보강). 조사 중(에이전트) | 패치 때만 |
| `slang.yaml` | 약어·은어 → `items.json` id. 예: 슬가→?, 스웹벨트→?, 자룬→Jah, 지존참→3/20/20 스몰참, 올으뜸, 쌍패, 모너크, 직득, 미확, 대리작, 맨땅, 노거래 | 나무위키 용어 문서, 인벤/디시 약어글 + **친구 자신의 어휘**(아래 9.2) | 수시, 사람이 검토 |
| `value.yaml` | 아이템/옵션 조합별 가치 구간. 단위 두 벌: `rune_unit`(자룬/베르룬 환산)과 `krw`(현금 원화). 범위로 기록(`krw: [50000, 90000]`) | 디시 디아2갤 시세표, 인벤 거래글, 아이템베이 시세, **친구 영상의 현금 카드**("현금 7만원이 넘는 지존참") | 래더 시즌마다 스냅샷(`value_ladder15.yaml`) |
| `events.yaml` | 게임 이벤트 사전: 드랍(라벨 색별), 감별(미확 → 툴팁), 룬워드 제작, 큐브 조합, 소켓, 공포의 영역, 보스(안다/메피/바알/디아), 횃불·애니 퀘스트, 모자이크 재료. 각 이벤트의 **화면 단서**(ROI·색·텍스트) 와 **쇼츠 가치** | 게임 지식 + ep59 같은 실제 프레임에서 템플릿 추출 | 패치 때만 |

### 9.2 친구가 가진 지식을 데이터로 뽑는 법 (가장 싸고 정확)
1. **제목·해시태그 마이닝**: 채널 영상 전체의 제목/설명/해시태그(#지존참 #올으뜸스몰참 #비싼스몰참 #고급룬 #자룬)를 수집 → 친구 어휘 빈도표 → `slang.yaml` 초안. 제목의 "현금 N만원" 문구는 `value.yaml`의 1차 데이터.
2. **배너 OCR 누적**: 편집본 40여 편의 득템 배너 토큰을 전부 모으면 친구가 "적을 가치가 있다"고 본 아이템 집합과 그의 표기법이 그대로 나온다. 토큰 → 사전 매칭 실패분이 곧 사전에 추가할 항목.
3. **30분 인터뷰 체크리스트** (한 번만): 배너에 적는 기준, 쇼츠로 만들고 싶은 순간 Top 5, 자주 쓰는 약어 20개의 뜻, 시세 보는 곳, "이건 절대 쇼츠감"과 "이건 롱폼용" 예시 각 3개.
4. **리뷰 루프**: 검출된 아이템 이벤트마다 친구가 `가치 상/중/하` 한 글자만 찍는 시트 → `value.yaml` 보정 + hit@K 라벨.

### 9.3 LLM·검색을 보조로 쓰는 범위
- 사전 초안 작성(영문 아이템 → 한글 공식명, 약어 후보)은 LLM(Claude)이 만들고 **소스 URL과 함께** 사람이 검토. 로컬 LLM은 안 씀(정확도·비용 대비 이득 없음).
- 시세는 LLM이 아니라 소스에서. LLM은 "범위 추정"만, 반드시 `source`·`as_of` 필드와 함께 기록.

### 9.4 지식이 신호에 들어가는 자리
- `item_banner` / `item_tooltip` / `d2_item_label` 의 OCR 텍스트 → `slang.yaml` → `items.json` id → `value.yaml` 가치 → **Payoff 점수**와 **overlay_text**.
- `events.yaml` 의 화면 단서 → `ui_state`(억제 마스크) 와 결과형 이벤트 템플릿.
- 매칭 실패 토큰은 `reports/unknown_tokens.md` 에 쌓여 다음 사전 갱신 입력이 된다. **지식 보강도 recall 지표로 측정**: "배너 토큰 중 사전 매칭률".
