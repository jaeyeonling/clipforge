# 분석 코어

영상에서 "쓸 만한 순간"을 찾고 순위를 매기는 부분이에요. 프로세스·API·배포는 [ARCHITECTURE.md](ARCHITECTURE.md), 이 구조에 이르기까지의 실험과 결정은 [notes/ENGINE_LOG.md](notes/ENGINE_LOG.md) 에 있어요.

## 문제 정의

| | 편집본 → 쇼츠 | 원본 → 편집 포인트 |
|---|---|---|
| 입력 | 10~15분 편집본 (이미 하이라이트가 촘촘함) | 수 시간짜리 방송 녹화 |
| 문제 | **순위 매기기**: 몇 개 안 되는 쇼츠감을 위로 | **걸러내기**: 남길 구간을 놓치지 않으면서 볼 양을 줄이기 |
| 정답 | 사람의 쓸 만함 / 안 씀, 올린 쇼츠 역매핑, 제목의 득템 | 편집본을 원본에 정렬해 살아남은 구간 |
| 1순위 지표 | hit@K · MRR | recall (목표 ≥ 95%), coverage (목표 ≤ 10%) |

코드 주석의 **Phase 1** 은 편집본 → 쇼츠, **Phase 2** 는 원본 → 편집 포인트를 말해요. 두 경우는 같은 코드를 써요. 다른 것은 입력, 정답의 출처, 지표, 출력 형태뿐이에요. 게임 프로필 · 신호 · 평가는 공유해요.

원칙은 하나예요. **측정할 수 있어야 바꾼다.** 신호를 더하거나 가중치를 바꾸면 정답 셋에 대한 지표가 어떻게 바뀌는지 같이 봐요.

## 1. 영상 읽기 (prep)

FFmpeg 한 번의 디코드에서 필요한 것을 전부 뽑아요. 이후 단계는 원본 영상을 다시 읽지 않아요.

- `audio.wav` 16kHz 모노 (전사 · 음량 · 오디오 지문 공용)
- `frames/` 1초에 한 장, 최대 1080p (4K 원본은 1080p 로 줄여요)
- `rois/<영역>/` 득템 배너 · 채팅처럼 OCR 할 영역은 **원본 해상도로** 잘라 둬요. 4K 에서 배너 글자 높이가 45px 이라 줄이면 못 읽어요
- `cuts.json` 장면 전환(scdet). 편집본에서만 켜요
- NVDEC 를 먼저 시도하고 안 되면 CPU 로. 4K 11.7분 편집본이 약 2분 50초 걸려요

## 2. 신호

신호는 `@signal(name)` 으로 등록하는 함수예요. 캐시 폴더를 받아 **곡선**(시각별 값) 또는 **이벤트**(구간 + 라벨)를 돌려줘요.

| 신호 | 입력 | 출력 | 방법 |
|---|---|---|---|
| `item_banner` | rois/banner | 이벤트 `append · appear · switch · reset` | 3초 간격 OCR → 바뀐 구간만 1초로 다시. 3초 이상 유지된 "안정 상태" 사이의 전이만 이벤트로 (OCR 흔들림 제거). 글자가 늘어난 시각 = 득템 |
| `chat_burst` | rois/chat | 곡선 | 채팅 영역 픽셀 변화율. 채팅이 터지는 순간 |
| `chat_text` | rois/chat | 이벤트 (새 메시지) | 변화가 있는 초만 OCR, "닉 : 메시지" 재구성, 직전 초와 비교해 새 줄만 |
| `speech_keyword` | transcript.json | 이벤트 (강 · 중 · 약 · 득템) | 리액션 · 득템 어휘 (`games/common.yaml`), 8초 쿨다운 |
| `audio_loudness` | audio.wav | 곡선 | RMS dB, 중앙값 대비 |
| `frame_motion` | frames | 곡선 | 1초 프레임 차이 |
| `edit_emphasis` | frames | 이벤트 `zoom · note` | 편집자가 강조한 구간: HUD 가 사라짐(줌·카드), 밝은 사각형(메모장) |
| `cut_density` | cuts.json | 곡선 | 30초 창의 컷 수 (편집본) |
| `ui_state` | frames | 이벤트 `inventory · left_panel · offscreen` | 패널 제목 OCR("소지품"·"캐릭터")과 HUD 구슬. 세로 크롭 중심과 억제에 써요 |

결과는 `cache/<id>/<신호>.json` 에 남고 다시 계산하지 않아요. OCR 은 RapidOCR(ONNX, CPU), 패널 제목처럼 위치가 정해진 글자는 인식 전용 모델로 크롭당 0.01~0.05초예요.

## 3. 쇼츠 후보와 점수 (편집본)

### 앵커 → 창

쇼츠 후보는 "점수가 높은 구간"이 아니라 **사건(앵커)** 에서 시작해요. 앵커는 득템 배너 추가 → 편집 강조 → 채팅 폭주 → 리액션 발화 순으로 모아요(10초 안의 앵커는 합쳐요).

앵커마다 두 길이를 만들어요.

| 변형 | 앵커 전 | 앵커 후 | 의도 |
|---|---|---|---|
| 한방형 `short` | 5초 | 12초 | 가장 센 순간만 (15~20초) |
| 서사형 `story` | 12초 | 22초 | 드랍 → 템 창 → 리액션 한 호흡 (30~45초) |

경계는 **말의 경계**에 붙여요. 전사가 있으면 Whisper 단어 경계를, 없으면 에너지 기반 발화 검출을 써요. 끝점이 말 중간이면 그 말이 끝날 때까지(최대 8초) 늘리고, 끝 직후 3초 안에 리액션이 시작하면 그 리액션 끝까지 늘려요. 시작점 1초 안에 장면 전환이 있으면 거기서 시작해요. 길이는 15~60초로 묶어요.

### 다섯 축

| 축 | 계산 | 기본 가중치 |
|---|---|---|
| 득템 payoff | 창 안에 배너 추가가 있으면 1 | 0.35 |
| 리액션 reaction | 앵커 뒤 리액션 발화 세기(강 1.0 / 중·득템 0.7) · 편집 강조(0.6) | 0.25 |
| 채팅 반응 chat | 창 안 채팅 변화율의 최대값 ÷ 영상 99분위 | 0.15 |
| 완결성 completeness | 앵커 전 3초 이상 맥락 · 앵커 뒤 3초 이상 반응 · 시작·끝이 말 쉼에 걸림 | 0.15 |
| 첫 2초 hook | 첫 2초에 소리·사건이 있으면 1, 줌·조용한 시작이면 0 | 0.10 |

감점: 장면 전환이 2개를 넘으면 하나당 −0.05, 길이가 15~60초를 벗어나면 −0.2, **리액션 < 0.3 이면서 채팅 < 0.5 이면 −0.15**(득템만 있고 반응이 없는 "임팩트 없음").

### 같은 순간은 하나만

앵커가 45초 안이거나 창이 1/3 이상 겹치면 같은 순간으로 보고, 두 변형을 통틀어 하나만 남겨요. 대표는 그 순간의 **원인(가장 이른 득템 앵커)을 담은 창** 중 점수가 가장 높은 것이에요. 드랍부터 리액션까지 이어지는 창이 리액션만 있는 줌 창보다 앞서게 하려는 규칙이에요.

### 판정으로 가중치 맞추기

사람의 쓸 만함 / 안 씀을 그 초안의 다섯 축 점수와 짝지어 가중치를 다시 맞춰요 (`preference.py`).

- 판정이 6개 미만이거나 한쪽만 있으면 기본값을 그대로 써요.
- 기본 가중치를 중심으로 당기는 L2 로지스틱 회귀로 축 계수를 맞추고, 음수는 0으로 자른 뒤 합을 1로 맞춰요.
- 판정 수 n 에 비례해서만 옮겨 가요: `w = a·학습값 + (1−a)·기본값`, `a = n / (n + 20)`. 판정 20개에서 반반이에요.
- 판정할 때 축 점수를 함께 남겨서(`labels/<id>.shorts.axes.json`) 후보를 다시 만들어 구간이 바뀌어도 판정이 학습에서 빠지지 않아요.

### 제목과 자막

- 상단 제목 1줄째는 창 안에서 리액션 어휘 가중치가 가장 큰 대사를 20자로 다듬어요("와, 뭐야!"). 채팅이 앵커면 반응 어휘가 가장 센 채팅 원문을 인용해요(닉네임은 쓰지 않아요).
- 2줄째는 배너 OCR 토큰을 아이템 사전으로 정규화한 이름 + "직득!". 뜻을 모르는 약어는 빼요.
- 대사 자막은 전사 세그먼트를 18자 단위로 나눠(단어 시각 사용) 굽고, 같은 큐를 SRT 로도 내요.

## 4. 렌더 (세로 초안)

확정 레이아웃 `card`: 위에 손글씨 제목 띠, 가운데 게임 화면 정사각 크롭, 아래에 방송 채팅 영역을 그대로. 크롭 중심은 `ui_state` 를 따라 **즉시 점프**해요(인벤토리면 오른쪽, 캐릭터 창이면 왼쪽). 패닝은 어색하다는 피드백으로 기본은 컷이에요. 자막은 libass 로 굽고, 인코딩은 NVENC 예요. 레이아웃 결정 과정은 [design/SHORTS_LAYOUT.md](design/SHORTS_LAYOUT.md).

한글은 `textdraw.py` 한 곳에서만 그려요. 굵기와 테두리는 오프셋 스탬핑으로, 글자 단위 폰트 폴백(손글씨 → 고딕)으로. PIL 의 `stroke_width` 는 일부 글리프를 속 빈 획으로 그려서 쓰지 않아요(`scripts/check_fonts.py` 가 지켜요).

## 5. 편집 포인트 (원본)

1. 곡선 신호는 z-score 로, 이벤트 신호는 비대칭 커널(예: 득템 앞 8초 · 뒤 6초)로 0~1 곡선이 돼요.
2. 0.5초 간격으로 맞춰 가중합 → 임계값을 넘는 구간 → 앞뒤 여유 · 가까운 구간 병합 → 짧은 것 버림.
3. 원본은 길어서 OCR 이 무거운 채팅 신호와 편집본에만 의미 있는 신호는 빼고, 득템 배너는 화면이 바뀔 때만 OCR 해요.

이 판정 층은 같은 입력(곡선들)을 받아 같은 출력(구간)을 내는 작은 분류기로 바꿀 자리예요. 정답이 수백 개 쌓이면 바꿔요.

## 6. 정답 만들기와 평가

- **정렬(align)**: 편집본의 각 2~3초 창을 원본에 오디오 랜드마크 지문으로 맞추고, 창 투표로 오프셋을 정한 뒤 경계를 다듬어 "살아남은 구간"을 `labels/<id>.csv` 에 써요. 같은 방법으로 올린 쇼츠를 편집본에 역매핑해 쇼츠 정답을 만들어요. 합성·재인코딩 테스트에서 경계 오차 0.35초 이하. 상세는 [design/ALIGN.md](design/ALIGN.md).
- **약한 정답**: 회차 제목의 득템 이름을 약어 사전으로 뽑아 배너 추가 토큰과 퍼지 매칭(≥ 85)하면 그 회차 1순위 순간의 시각이 나와요(± 30초).
- **지표**: 쇼츠는 hit@1 · hit@3 · MRR. 편집 포인트는 recall · precision · coverage 와 라벨 범주별 recall(어떤 종류의 순간을 놓치는지 → 다음에 보강할 신호).

## 7. 도메인 지식 (디아블로2 레저렉션)

| 파일 | 내용 | 출처 |
|---|---|---|
| `data/d2r/items.json` | 유니크 · 세트 · 룬 · 룬워드 · 참 · 베이스 1,308개, 영↔한 이름 | blizzhackers/d2data(MIT) 가공, `scripts/build_items.py` |
| `data/d2r/slang.yaml` | 약어·은어 → 아이템 id ("지존참", "스웹벨트", "자룬" …) | 커뮤니티 용어 + 방송 배너 표기 |
| `games/common.yaml` | 리액션 · 채팅 반응 어휘, 회차 종류별 신호 묶음, 정답 범주 | |

배너 OCR 토큰 → 약어 사전 → 아이템 id 로 이어지고, 매칭 실패 토큰은 다음 사전 갱신의 입력이 돼요. 사전 커버리지도 "배너 토큰 중 매칭률"로 측정해요.

## 알려진 한계

- 기본 가중치는 편집본 한 편의 판정으로 맞춘 초기값이에요. 판정이 쌓이면서 학습이 조정해요.
- 원본 VOD 실측은 아직이에요. 정렬은 합성·재인코딩 테스트로만 검증했어요.
- 디아블로2 한국어 클라이언트 화면 배치에 맞춰져 있어요. 다른 게임은 [GAME_PROFILE.md](GAME_PROFILE.md) 로 프로필을 더해야 해요.
